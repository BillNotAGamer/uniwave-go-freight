## B. Executive Recommendation

Recommended MVP: build an Admin-only read-only Audit Viewer at `/admin/audit`, protected server-side by the existing `AUDIT_LOGS_READ` permission.

Use a dedicated feature area, for example `src/features/admin/audit/`, with:

- `policy.ts` for viewer authorization.
- `validators.ts` for query params and cursor validation.
- `queries.ts` for server-side read model.
- `presentation.ts` for action labels and safe snapshot presentation.
- `types.ts` for a safe DTO.

Do not return raw `audit_logs.before` / `audit_logs.after` JSON to the browser. Stored audit evidence should remain immutable, but viewer DTOs should render only approved, sanitized, field-level summaries.

Recommended implementation prerequisite: add one narrow index-only migration for newest-first pagination: `(created_at DESC, id DESC)`. The existing schema is otherwise sufficient for an MVP.

## D. Current Audit Write Architecture

REPOSITORY-PROVEN:

- Helper: `src/lib/audit/log.ts`
- `logAuditEvent(db, input)` inserts into `audit_logs`.
- The helper serializes `before` and `after` with `JSON.parse(JSON.stringify(value))`.
- `action`, `entityType`, and `entityId` are free-form strings.
- `reason` is optional and stored as null when omitted.
- `createdAt` is database default time.
- Current production call sites pass transaction objects (`tx`) to `logAuditEvent(...)`, so business state and audit row commit atomically at existing call sites.

INFERRED:

- The helper accepts any insert-capable DB object, not only a transaction type. Future code should preserve the existing transaction convention with tests.

## G. RBAC Recommendation

Recommended policy: Admin-only through existing `AUDIT_LOGS_READ`.

REPOSITORY-PROVEN:

- `PERMISSIONS.AUDIT_LOGS_READ` exists with value `audit-logs:read`.
- Sale does not have it.
- Accountant does not have it.
- Admin receives all declared permissions through the role permission map and admin shortcut behavior.

Rationale:

- Audit logs include Admin User Management events, session revocation metadata, temporary password reset events, buying/profit-adjacent charge snapshots, tax override reasons, internal export metadata, Drive file/folder IDs, and storage keys.
- Accountant can see accounting data in normal workflows, but the global audit stream includes Admin/security/user-management events outside the accountant boundary.
- Per-action/per-entity filtering would be materially more complex and risk leaking privileged context.

## H. Snapshot Security Analysis

REPOSITORY-PROVEN SAFE:

- `user.create` audit uses `toUserAuditSnapshot(...)` and does not include the temporary password or credential hash.
- `user.password_set_by_admin` stores target id, role, active/deleted state, and `revokedSessionCount`; it does not include password/hash.
- `user.sessions_revoked` stores `targetUserId` and `revokedSessionCount`; it does not include session tokens, session IDs, IP addresses, or user agents.

REPOSITORY-PROVEN UNSAFE FOR RAW VIEWER DISPLAY:

- Shipping Note create/update/submit/review/check snapshots may include customer, shipper, consignee, agent, route, exchange rate, status, and actor fields.
- Selling charge snapshots include prices and amounts.
- Buying charge snapshots include vendor/agent text, unit price, amounts, and other accounting-sensitive data.
- Tax assignment/override snapshots include tax rule identity, VAT percent, VAT amount, override flag, and override reason.
- Export generated snapshots include `artifactStorageKey`, checksum, file name, artifact size, MIME type, and charge counts.
- Drive audit snapshots include Drive file id, Drive folder id, checksum, upload status, error code, and retry/reconciliation metadata.

UNKNOWN / DEFENSE-IN-DEPTH:

- `logAuditEvent(...)` accepts arbitrary unknown snapshots and serializes them without a sanitizer. A future producer could accidentally store keys such as `password`, `token`, `secret`, or provider credentials.

Conclusion: raw JSON must not be the browser DTO.

## I. Safe Audit DTO

Recommended DTO:

```ts
type AuditViewerItem = {
  id: string;
  action: string;
  actionLabel: string;
  category: "shipping_note" | "charge" | "tax" | "export" | "user" | "unknown";
  entityType: string;
  entityId: string;
  entityLabel: string | null;
  entityHref: string | null;
  actor: {
    id: string | null;
    name: string | null;
    email: string | null;
    display: string;
  };
  reason: string | null;
  createdAt: Date;
  changes: AuditViewerChange[];
};
```

`AuditViewerChange` should be a safe presentation object:

```ts
type AuditViewerChange = {
  field: string;
  label: string;
  before: string | null;
  after: string | null;
  sensitive: boolean;
};
```

Do not expose raw Drizzle rows, raw `users`, raw `accounts`, raw `sessions`, raw `shipping_note_exports`, or raw JSON snapshots.

## J. Snapshot Presentation Strategy

Recommended strategy: hybrid safe presentation adapters.

- Keep stored audit rows immutable.
- Build action/entity-specific allowlist presenters for known actions.
- Apply a recursive denylist sanitizer as a fallback for unknown/future actions.
- For unknown actions, show canonical action/entity/time/actor/reason plus only safe scalar fields that pass sanitizer.
- Preserve the canonical action string in the UI for technical auditability.
- Map known actions to human labels and categories in the presentation layer.

Do not rewrite historical audit rows to fit new UI requirements.

## K. Actor / Entity Resolution

Actor resolution:

- Left join `users` by `audit_logs.actor_user_id`.
- Display name plus email when available.
- Inactive/soft-deleted actors should still display their retained user row fields.
- If `actorUserId` is null or the user row is gone, display `Unknown actor` or `Deleted actor`; do not invent identity.
- Do not query accounts or sessions for actor display.

Entity resolution:

- `shipping_note`: resolve `jobsheetNo` only.
- `shipping_note_charge`: resolve charge name, section, and parent `jobsheetNo` if feasible.
- `shipping_note_export`: resolve file name, export type/version, status, and parent `jobsheetNo`; do not expose storage key by default.
- `tax_rule`: resolve code/name.
- `user`: resolve name/email/account status.

All entity label queries must select small safe column sets only.

## L. Filtering / Search

Recommended MVP filters:

- `action`: exact canonical action string from a known catalog or string validator.
- `entityType`: exact entity type.
- `entityId`: exact id.
- `actorId`: UUID/text id validated as a user id.
- `from`: date/time lower bound.
- `to`: date/time upper bound.
- `search`: limited text search over action, entity type, entity id, actor name/email, and resolved entity labels.

Do not implement arbitrary JSON filters or raw SQL fragments.

## M. Pagination / Ordering

Recommended default ordering:

- `createdAt DESC`
- `id DESC` as deterministic tie-breaker

Recommended pagination: keyset/cursor pagination using `(createdAt, id)`.

Rationale:

- `audit_logs` is append-heavy.
- Offset pagination becomes progressively expensive as the table grows.
- Keyset pagination pairs naturally with newest-first audit review.

MVP limit: default `50`, maximum `100`.

## N. Index / Migration Assessment

Current index support:

- Existing `(entity_type, entity_id)` index supports entity-history lookup.

Missing for recommended viewer:

- No `created_at` index for default newest-first list.
- No `actor_user_id` index for actor filter.
- No `action` index for action filter.

Recommended minimum implementation migration:

```sql
CREATE INDEX audit_logs_created_at_id_idx
ON audit_logs (created_at DESC, id DESC);
```

Optional later indexes after observed usage:

- `audit_logs_actor_created_idx` on `(actor_user_id, created_at DESC, id DESC)`.
- `audit_logs_action_created_idx` on `(action, created_at DESC, id DESC)`.
- Existing `audit_logs_entity_lookup_idx` is sufficient for entity detail/history lookup.

Migration required for production-quality MVP: yes, index-only. No migration was created by this audit.

Current migration status in this conversation:

- `drizzle/0003_hard_titania.sql`: not applied.
- `drizzle/0004_clean_power_man.sql`: not applied.

## O. Route / UI Architecture

Recommended route: `/admin/audit`.

Why:

- Current Admin Users route uses `/admin/users`.
- `/admin/audit` is concise and consistent with an Admin-only back-office area.
- It avoids implying raw log-file access through a path like `/admin/audit-logs`.

Recommended UI:

- Header.
- Filter form.
- Audit table.
- Columns: Time, Actor, Action, Entity, Reason, Details.
- Inline expandable details per row.
- Simple category badges are acceptable, but meaning must not depend only on color.
- No charts, analytics dashboard, CSV export, edit/delete controls, or extra detail route in MVP.

Server-side:

- Query/filter/pagination must run on the server.
- Client-side code may manage filter form state, links, and expand/collapse only.

## P. Historical Compatibility

Requirements:

- Old rows may have missing `before`, `after`, or `reason`.
- Unknown future action strings must not crash the viewer.
- Entity label resolution can fail for deleted or historical entities; the row still renders with entity type/id.
- Stored snapshot shapes may differ across phases; presenters must tolerate missing fields.
- Raw `before`/`after` remains immutable evidence in the database, but the UI renders only sanitized/allowlisted summaries.

## Q. Timezone / Display

REPOSITORY-PROVEN:

- Current UI frequently uses `new Date(value).toLocaleString()` without an explicit timezone.
- No repository-wide Vietnam timezone display helper was found.

Recommendation:

- Audit Viewer should display timestamps in an explicit business timezone, preferably Vietnam time (`Asia/Ho_Chi_Minh`) unless Product/Ops chooses otherwise.
- DB timestamps remain unchanged.
- Avoid accidentally changing display based on the browser or server locale for an audit surface.

## R. Retention / Growth

DECISION REQUIRED:

Recommended MVP:

- Retain audit logs indefinitely until Product/Ops defines a retention policy.
- Do not add deletion/retention jobs in the viewer slice.
- Add the keyset pagination index before exposing broad browsing.

## S. Test Strategy

Pure/unit tests:

- Permission policy: Sale denied, Accountant denied, Admin allowed through `AUDIT_LOGS_READ`.
- Filter validators: action, entity type, actor id, date range, limit, cursor.
- Cursor encode/decode and invalid cursor rejection.
- Known action label mapping and unknown-action fallback.
- Recursive sensitive-key sanitizer, including nested keys.
- Action-specific presenters for representative known actions.

Read-model/integration tests, when DB authorization is available:

- Admin list access succeeds.
- Sale and Accountant list access denied before query data leaks.
- Newest-first ordering by `created_at DESC, id DESC`.
- Filters by action, entity type, actor, entity id, and date range.
- Soft-deleted actor row still resolves safe identity.
- Null actor displays safely.
- DTO does not include raw snapshots or sensitive keys.

Security tests:

- Synthetic audit rows containing `password`, `passwordHash`, `token`, `sessionToken`, `accessToken`, `refreshToken`, `privateKey`, `secret`, `credential`, `databaseUrl`, `artifactStorageKey`, and nested variants must not expose those values.
- User-management audit rows render `user.create`, `user.role_change`, `user.deactivate`, `user.reactivate`, `user.soft_delete`, `user.sessions_revoked`, and `user.password_set_by_admin` without credentials.
- Shipping Note rows render approve/lock/unlock/cancel/reopen as field changes.
- Drive rows render upload success/failure without credentials or storage keys.
