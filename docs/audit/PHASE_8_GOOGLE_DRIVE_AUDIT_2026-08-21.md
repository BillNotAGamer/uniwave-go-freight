## B. Executive Recommendation

Recommended Phase 8 MVP architecture: add durable artifact binary storage before Google Drive upload, then upload a specific `shipping_note_exports.id` from that persisted binary source to Google Drive.

This is a prerequisite architecture, not optional polish. The current repository persists export metadata and checksum only. It does not persist XLSX/PDF bytes, object keys, local file paths, temporary files, or database blobs. After the current HTTP export request completes, the generated artifact bytes are gone.

Do not implement Phase 8 by regenerating old artifacts for Drive. XLSX V2 has a pinned template, but byte-identical regeneration is still sensitive to ExcelJS/package/runtime details. PDF V1 is even less suitable for byte-identical regeneration because React-PDF output can vary with library version, font engine behavior, timestamps, Node version, and PDF metadata.

Do not implement Phase 8 as a note-level `drive_uploaded` or `exported` Shipping Note status. Drive state belongs to a specific export artifact record.

Recommended implementation slicing:

1. Phase 8A: persist generated XLSX/PDF bytes to durable object storage and add the minimal schema needed to reference the persisted object and represent Drive upload state independently.
2. Phase 8B: implement Admin-only Drive upload for a specific stored export record using a service account and configured Shared Drive/root folder.
3. Phase 8C: add a minimal export-history panel for Accountant/Admin, with Admin-only upload/retry controls.

## C. Current Artifact Architecture

Current XLSX and PDF generation share the same source data model:

- `getInternalShippingNoteExportDataForUser(...)` enforces `SHIPPING_NOTES_EXPORT_INTERNAL`.
- Sale is denied by permission.
- Accountant/Admin can export eligible notes.
- Eligible Shipping Note statuses are `checked`, `approved`, and `locked`.
- Denied statuses are `draft`, `submitted`, `accounting_reviewing`, `cancelled`, and `exported`.
- `shipping_notes.status` is not changed by XLSX or PDF generation.

Repository-proven export contracts:

| Artifact | Export type | Persisted version | Artifact identifier | MIME |
| --- | --- | ---: | --- | --- |
| XLSX V2 | `excel` | `2` | `internal-v2` template | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
| PDF V1 | `pdf` | `1` | `internal-pdf-v1` layout | `application/pdf` |

Current export persistence:

- Pending row is inserted into `shipping_note_exports`.
- Generator produces bytes in process memory.
- SHA-256 is computed over the generated bytes.
- Export row is updated to `generated` or `failed`.
- Audit event is written for generated/failed.
- Bytes are returned in the HTTP response.
- No durable binary artifact reference is stored.

Evidence:

- `src/lib/db/schema.ts` defines `shipping_note_exports` with metadata fields only: `exportType`, `version`, `status`, `driveFileId`, `driveUrl`, `fileName`, `checksum`, `errorMessage`, `generatedById`, and `generatedAt`.
- `src/features/shipping-notes/export/generator.ts` returns an XLSX `ArrayBuffer` and checksum.
- `src/features/shipping-notes/export/pdf/generator.tsx` returns a PDF `Buffer` and checksum.
- `src/app/api/shipping-notes/[id]/exports/internal-xlsx/route.ts` and `src/app/api/shipping-notes/[id]/exports/internal-pdf/route.ts` return generated bytes directly in the response.
- No repository source contains a Google Drive adapter, object storage adapter, artifact storage key, database blob, or persisted local file path.

Classification: `REPOSITORY-PROVEN`, P1.

## D. Artifact Byte Availability

| Artifact | Bytes exist during request | Bytes persisted afterwards | Regeneratable | Versioned | Checksum available |
| --- | --- | --- | --- | --- | --- |
| XLSX V2 | Yes, in memory as generated workbook bytes | No | Functionally regeneratable from current code/template, but byte identity is not guaranteed across package/runtime changes | Yes, `version = 2`, template `internal-v2`, pinned template SHA-256 | Yes, stored SHA-256 of generated bytes |
| PDF V1 | Yes, in memory as React-PDF buffer | No | Functionally regeneratable from current code/fonts, but byte identity is not guaranteed | Yes, `version = 1`, layout `internal-pdf-v1` | Yes, stored SHA-256 of generated bytes |

Conclusion: a `shipping_note_exports` row is not currently a retrievable artifact. It is an audit/metadata record for an artifact that was generated and returned at request time.

## E. Upload Architecture Options

| Option | Assessment |
| --- | --- |
| A. Generate + upload in same request | Uses exact bytes and avoids regeneration. However, it couples local artifact generation to Drive latency/failures, makes browser/client retries hard to deduplicate if the export ID is not stable before retry, risks serverless timeouts, and still has DB-failure-after-Google-success recovery concerns. Acceptable only for a narrow "generate new Drive artifact" action, not for uploading existing generated records. |
| B. Generate, return, then regenerate for Drive | Not recommended. Current export rows have checksum but no bytes. Regenerating and comparing checksum would often block valid historical uploads after package/runtime/layout changes, especially for PDF. Uploading regenerated bytes with a different checksum would violate artifact identity. |
| C. Persist binary artifact outside Drive first | Recommended. Store exact generated bytes in durable app-owned storage, store an object key on `shipping_note_exports`, then upload that exact object to Drive. This supports retry, exact checksum verification, historical export selection, and future workers. It adds infrastructure and a schema migration, but it is the only design that faithfully uploads a specific generated artifact. |
| D. Upload during initial generation but separate download/upload operations | Viable only if the "upload" operation has a real source for bytes. In the current repository, a later upload operation cannot source bytes from `shipping_note_exports`; it would have to regenerate or fail. With durable artifact storage added, this collapses into Option C. |

## F. Recommended Upload Architecture

Choose Option C: durable app-owned artifact storage first, then Drive upload from the stored artifact.

Recommended flow for generation after Phase 8A:

```text
authorized export request
-> canonical internal export DTO
-> generate XLSX/PDF bytes
-> compute local SHA-256
-> store bytes in durable artifact storage
-> persist shipping_note_exports:
     status = generated
     fileName
     checksum
     generatedById
     generatedAt
     artifactStorageKey
     artifactSizeBytes
-> return download bytes if the request was a download
```

Recommended flow for Drive upload after Phase 8B:

```text
POST /api/shipping-note-exports/{exportId}/drive
-> same-origin/session check
-> require upload permission
-> load export + owning shipping note
-> verify export has persisted bytes and checksum
-> short-circuit if DB already has driveFileId/driveUrl
-> search Drive by appProperties.uniwaveExportId
-> if found, reconcile DB
-> read exact bytes from artifact storage
-> verify SHA-256 equals stored checksum
-> upload to configured Drive folder
-> DB transaction:
     save driveFileId, driveUrl, driveUploadedAt, driveUploadStatus
     audit
```

Do not hold a database transaction open while calling Google.

## G. Authentication Model

Recommended MVP authentication: Google service account, server-only.

Why:

- Fits the current server-only export architecture.
- Avoids per-user OAuth consent and refresh-token storage.
- Keeps ownership with an integration identity rather than individual employees.
- Works well with a company Shared Drive or a folder explicitly shared with the service account.
- Easier to test with a fake adapter because application users do not need Google tokens.

Not recommended for MVP:

- OAuth user delegation: higher complexity, refresh-token storage, per-user ownership, revocation handling, and more difficult support.
- Workspace domain-wide delegation: powerful but requires Google Workspace admin setup and should not be assumed.

`DECISION REQUIRED`: confirm whether Uniwave has Google Workspace and whether IT can create a service account and grant it access to a company-controlled Shared Drive or folder.

## I. Artifact Source-of-Truth Contract

Recommended source-of-truth split:

| Domain | Source of truth |
| --- | --- |
| Business Shipping Note data | PostgreSQL |
| Export artifact metadata | `shipping_note_exports` |
| Export binary bytes | App-owned durable artifact storage |

## J. Export Record Lifecycle Analysis

Current lifecycle:

```text
pending -> generated
pending -> failed
```

The enum also includes `uploaded`, but no current code sets it.

Current fields are adequate for generation-only metadata. They are not adequate for a robust Drive upload lifecycle because a generated artifact and Drive upload are separate facts.

Recommended future lifecycle:

```text
Artifact generation:
pending -> generated
pending -> failed

Drive upload:
not_uploaded -> uploading -> uploaded
not_uploaded/upload_failed -> uploading -> upload_failed
uploaded -> uploaded   // idempotent retry
```

`shipping_note_exports.status` should remain the artifact generation status. If implementation chooses to set `status = uploaded`, it must still preserve independent Drive failure state somewhere. Otherwise the model cannot accurately represent "artifact exists, Drive upload failed".

## K. Drive Failure State Analysis

Critical case:

```text
PDF generated successfully
checksum persisted
Drive upload fails
```

If `status` is changed to `failed`, the row incorrectly suggests artifact generation failed. If `status` stays `generated`, the existing schema has no structured field for Drive failure beyond overloading `errorMessage`.

Recommendation:

- Keep artifact `status = generated`.
- Add Drive-specific status/error metadata.
- Persist sanitized Drive error code/message separately from generation error.
- Audit Drive upload failure separately.

Recommended Drive failure semantics:

| Failure | Artifact status | Drive status | Retry? |
| --- | --- | --- | --- |
| Missing Drive config | `generated` | `upload_failed` | No until config fixed |
| Auth/private key invalid | `generated` | `upload_failed` | No until credential fixed |
| Permission denied/folder missing | `generated` | `upload_failed` | No until IT fixes folder access |
| 429/rate limit | `generated` | `upload_failed` | Yes |
| 5xx/network timeout | `generated` | `upload_failed` | Yes |
| Checksum mismatch before upload | `generated` | `upload_failed` | No; block upload and investigate |

## L. Schema / Migration Assessment

Migration required: yes, if Phase 8 must correctly upload specific generated artifacts and represent Drive upload failures.

Existing fields:

- Enough for generation metadata: `status`, `fileName`, `checksum`, `generatedById`, `generatedAt`.
- Enough for final Drive success metadata only: `driveFileId`, `driveUrl`.
- Not enough for binary source: no storage key/path/blob.
- Not enough for Drive state: no upload status, no upload timestamp, no Drive-specific error field.
- Not enough for folder/reconciliation auditing: no stored Drive folder ID.

Minimal proposed schema delta:

| Table | Column | Type | Nullable/default | FK/index | Reason |
| --- | --- | --- | --- | --- | --- |
| `shipping_note_exports` | `artifact_storage_key` | text | nullable | unique index when non-null | Durable pointer to exact generated bytes |
| `shipping_note_exports` | `artifact_size_bytes` | integer | nullable | none | Response/storage sanity check |
| `shipping_note_exports` | `artifact_mime_type` | text | nullable | none | Persist exact MIME used for upload |
| `shipping_note_exports` | `drive_upload_status` | enum/text | not null default `not_uploaded` | index optional | Independent Drive lifecycle |
| `shipping_note_exports` | `drive_uploaded_at` | timestamp(3) | nullable | optional | Query/report upload time |
| `shipping_note_exports` | `drive_folder_id` | text | nullable | optional | Reconciliation and audit context |
| `shipping_note_exports` | `drive_error_message` | text | nullable | none | Sanitized Drive-specific failure |

Do not add calculation or tax snapshot columns for this phase.

Historical export rows: leave storage key null. They should not be Drive-uploadable unless they are intentionally regenerated as a new export record or an operator manually backfills exact bytes, which the repository cannot currently do.

## M. Idempotency / Duplicate Prevention

Recommended idempotency key: `shipping_note_exports.id`.

Recommended behavior:

1. If `driveFileId` exists in DB, short-circuit and return the stored Drive metadata.
2. Otherwise search Drive for `appProperties.uniwaveExportId = exportId`.
3. If found, update DB with the existing Drive file ID/link and audit reconciliation/upload success.
4. If not found, upload a new file with appProperties.
5. Never rely on filename for idempotency because Google Drive permits duplicate filenames.

Recommended minimal Drive `appProperties`:

```text
uniwaveExportId
uniwaveShippingNoteId
uniwaveExportType
uniwaveExportVersion
uniwaveChecksumSha256
```

Do not put buying charges, profit, VAT amounts, customer names, private notes, credentials, or full audit details into Drive metadata.

Duplicate policy:

- Same export record retry: idempotently return/reconcile the existing Drive file.
- New export record for the same Shipping Note: create a separate Drive file.
- Do not overwrite an existing Drive file for a different export record.
- Do not update Drive file contents for a completed export record; generated artifacts should be immutable.

## N. DB Failure After Google Success

Distributed atomicity is impossible between PostgreSQL and Google Drive.

Critical case:

```text
Drive upload succeeds
DB update fails
```

Recommended recovery:

- Do not delete the Drive file automatically.
- On retry, search Drive by `appProperties.uniwaveExportId`.
- If a matching file is found and checksum/appProperties match, update DB with `driveFileId`, `driveUrl`, `driveUploadedAt`, and `drive_upload_status = uploaded`.
- Audit the reconciliation as the normal upload success or with a dedicated after snapshot flag such as `reconciledFromDrive: true`.

This requires appProperties and export-ID-specific upload routes.

## O. Concurrency / Retry

Recommended concurrency strategy:

- Use a DB compare-and-set guard to move `drive_upload_status` from `not_uploaded` or `upload_failed` to `uploading`.
- If already `uploading`, return a conflict or pollable status.
- If already `uploaded`, return existing Drive metadata.
- Still search Drive by appProperties before creating a file, because two app instances can race around DB/network boundaries.

Recommended retry classification:

| Error class | Retry policy |
| --- | --- |
| Network timeout | retry with small bounded attempts |
| 429 | retry respecting `Retry-After` when available |
| 5xx | retry with small bounded backoff |
| 401/invalid credential | non-retry until config fixed |
| 403/folder permission | non-retry until IT fixes access |
| 404 folder missing | non-retry until config fixed |
| quota exceeded | non-retry or delayed retry depending on Google error details |
| checksum mismatch | non-retry; block upload |

Add explicit timeout/abort handling around Google requests. Do not allow hung uploads to hold the request indefinitely.

## P. RBAC

Recommended permission: use existing `EXPORTS_UPLOAD`, not `SHIPPING_NOTES_EXPORT_INTERNAL`.

Reason: uploading to company Drive is an external side effect with storage, retention, duplication, and access-control implications. It is more privileged than downloading an internal artifact.

Current permission evidence:

- `SHIPPING_NOTES_EXPORT_INTERNAL` is granted to Accountant and Admin.
- `EXPORTS_UPLOAD` exists.
- Accountant does not have `EXPORTS_UPLOAD`.
- Admin has all permissions through centralized admin semantics.

Recommended MVP role matrix:

| Capability | Sale | Accountant | Admin |
| --- | ---: | ---: | ---: |
| View internal export/download | No | Yes | Yes |
| Generate internal artifact | No | Yes | Yes |
| Upload to Drive | No | No | Yes |
| Retry failed Drive upload | No | No | Yes |

Future product decision: Accountant may be granted `EXPORTS_UPLOAD` later if accounting operations own Drive filing.

## Q. Historical Reopen / Cancellation Policy

Generation eligibility and historical artifact upload eligibility are different policies.

Current generation eligibility:

```text
checked | approved | locked
```

Current generation denial:

```text
draft | submitted | accounting_reviewing | cancelled | exported
```

Recommended historical upload policy:

- Upload is based on a specific generated export record with persisted bytes and matching checksum.
- Current Shipping Note status should not be blindly reused for historical upload eligibility.
- Reopened notes: do not allow new generation while `accounting_reviewing`, but allow Admin-only upload of an already generated/stored historical artifact with clear UI labeling.
- Cancelled notes: do not allow new generation, but allow Admin-only upload of an already generated/stored historical artifact only as historical/archive material. UI and audit should show the current note status is `cancelled`.
- Locked notes: no special restriction; locked notes remain valid for generation and historical upload.

If Product wants cancelled artifacts never uploaded, that is a business decision. Engineering default is preservation plus Admin-only control because cancellation does not delete accounting history.

## R. Route / API Contract

Recommended route:

```text
POST /api/shipping-note-exports/[exportId]/drive
```

Reason: Drive upload acts on a specific artifact, not on a Shipping Note generally. A note can have multiple XLSX/PDF exports across corrections and versions.

Required request checks:

- Same-origin request metadata.
- Authenticated session.
- `EXPORTS_UPLOAD`.
- Export record exists.
- Export belongs to a non-soft-deleted Shipping Note the actor may operate on.
- Export has supported `exportType` and version dispatch.
- Export has durable bytes, checksum, MIME, and filename.
- Sale is denied.

Safe response:

```json
{
  "exportId": "...",
  "status": "uploaded",
  "driveFileId": "...",
  "driveUrl": "..."
}
```

Do not return credentials, access tokens, service account email/private key, full Google API payloads, or sensitive accounting details.

- client secrets
- access tokens
